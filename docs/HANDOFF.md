## 1. 下一阶段要完成什么

**当前最新目标：在用户的 Windows 开发电脑上，为 Pura X Max 和 Watch 5 开发一套独立的鸿蒙自用待办应用，手机和手表同步全部核心事项，不与 Windows 桌面版同步数据。**

本次交接仅整理现状、目标和接续流程，尚未创建鸿蒙工程、安装华为工具链或实现手机/手表功能。不要把下面的计划当作已有代码或已验证能力。

### 用户已明确的要求

- 设备名称按用户原话记录：`Pura X Max`（此前也写作 `puraxmax`）、`Watch 5`。设备的准确型号标识、系统完整版本和 API 支持范围待真机确认。
- 用户希望适用于“鸿蒙 7”。目前只知道这个目标称呼，没有核实设备系统、SDK 版本或相应 API，不能据此编造适配结论。
- 手机和手表必须保留全部核心事项的同步。不能把它悄悄缩减为仅同步通知或“下一条任务”。
- 不考虑与 Windows 应用的数据同步；鸿蒙版独立保存和管理自己的数据。
- 自用，不要求先上架应用市场。开发签名、调试安装的条件和有效期仍须查官方当前规则。
- 离线优先；断连时两端仍能使用，重连后补同步。不预设必须有服务器、云账号或公网连接。
- 产品原则：流程清晰、不冗余，同时保留自定义空间。
- 已知开发电脑是 **Windows**，不要重新询问 Windows 还是 macOS。

### 同步范围与待决定事项

核心同步范围至少包含：任务内容、清单/分组、子任务及勾选状态、四象限、每日计划归属和排序、问题跟踪分类及提出人/跟踪人/阶段、提醒相关配置、完成/恢复/删除状态。

“手机主界面完整，手表界面精简”是建议，不等于缩减手表持有的核心事项数据。手表如何浏览/编辑全部事项、完整历史日志是否双端复制、界面偏好是否同步、提醒由哪端触发以及如何防止重复提醒，仍需设计和确认。不要把“历史只在手机保存”等先前建议当作用户已批准的硬性要求。

## 3. 现有桌面产品的准确行为

### 界面与任务处理

- 默认进入“今日计划”。侧栏为今日计划、全部待办、已完成、问题跟踪、每日记录，另有自定义清单。
- 今日计划左侧是执行队列；右上是**当天未完成提醒**，按提醒时间排序；右下四象限是**全部未完成事项**，不是只看今日计划。
- 右侧“＋”加入今日，“✓”表示已加入；只是引用同一任务，不创建副本。点击标题可编辑，左右同步更新。
- 四象限：1 重要且紧急，2 重要不紧急，3 紧急不重要，4 不重要不紧急。
- 今日计划使用 ↑/↓ 排序，第一项标记“接下来做”。完成后列入下方已完成，下一项成为首项。取消完成按保留的计划位置恢复。
- “移出今日”不删除任务；删除任务会清理各日期计划里的引用。每天独立安排，不自动结转昨日任务。
- 搜索同时过滤今日队列和右侧参考区；搜索期间隐藏队列排序按钮。
- 右侧参考区可收起，选择存于本机浏览器存储；不属于 JSON 数据备份。
- 新建普通任务默认只显示标题和添加按钮。分类、清单、四象限、提醒折叠在选项里；进入问题跟踪时自动展开。
- 父任务完成状态与子任务完成状态独立，不会自动联动。
- 自定义清单删除后，任务移入收件箱。

### 问题跟踪

- 分类为普通待办或问题跟踪，与清单/项目分组相互独立。
- 字段：提出人 `reporter`、跟踪人 `tracker`、阶段 `stage`。
- 人员可为空，之后再补；阶段默认“分析中”，仅有 **分析中 / 等待回复 / 训练中 / 回归中**。
- 阶段和任务完成勾选相互独立，切换阶段不会自动完成。
- 可以按阶段筛选，按人员和阶段搜索。
- 改回普通待办时保留人员/阶段字段，方便再次切回。

### 每日记录与提醒

- 日志记录任务和子任务的新增、编辑、完成、恢复、删除；只改问题人员/阶段也会留记录。
- 每条记录保留操作时完整任务/子任务快照以及当时清单名称，后续删除或编辑不改写过去。
- 使用操作发生时的本地日期、时间归档；提醒时间保存为 ISO 时间。
- 可预览并导出选定日期或全部日期 Markdown。**当前是完整操作记录，不是自动去重、提炼后的工作日报。**
- 旧版无操作时间的数据不能倒推出过去每天做了什么；不会虚构历史。
- 桌面提醒每 10 秒检查一次，依赖应用运行且电脑唤醒。关窗口留托盘，退出托盘才完全停止；重开/唤醒后会检查尚未提醒的到期任务。
- 无开机自启、重复提醒、唤醒电脑。移动端不能照搬轮询方案，必须验证系统支持的提醒/后台机制。

### 桌面数据格式（可参考，不强制沿用为鸿蒙同步协议）

顶层 `version: 1`，包含：

- `groups: [{id, name}]`，必须有 `inbox` 收件箱。
- `tasks: [{id, title, groupId, quadrant, done, remindAt, notified?, children, category?, issue?}]`。
- `children: [{id, title, done}]`。
- `category: 'task' | 'issue'`，旧数据缺省按普通任务；`issue: {reporter, tracker, stage}`。
- `plans?: { 'YYYY-MM-DD': ['task-id', ...] }`，按日期保存顺序，包含保留位置的已完成事项。
- `history?: [{id, at, day, time, kind, task, groupName, childTitle?}]`，完整历史快照。

JSON 备份包含任务、分组、计划、历史，导入会确认后**替换**现有全部数据，不是合并。文件写入采用临时文件后替换；发现数据损坏时退出，避免覆盖。典型 Windows 数据路径是 `%APPDATA%\siji-todo\tasks.json`，最终以 Electron 实际 userData 路径为准。仓库不含用户真实桌面数据；clone 不会带来用户待办。

## 5. 产品方向：讨论过，但还没有实现的建议

用户认可“流程清晰不冗余、可自定义”的方向。以下是讨论过的后续建议，**不是已有功能，也不意味着必须在鸿蒙第一版全部实现**：

1. 收集 → 明确下一步 → 挑选今日任务并排序 → 执行/等待 → 完成 → 每日复盘。
2. 昨日未完成事项提供“今天继续 / 留在待办 / 暂缓 / 删除”，而非默认全部结转。
3. “等待回复”配合下一步行动和下次跟进时间。
4. 区分计划日期、截止日期、提醒时间，避免一个时间字段承担多种含义。
5. 日报提供精简工作总结与完整操作记录两种导出模式。
6. 将问题跟踪发展为可配置任务模板；可设置字段、阶段、必填/选填、默认值和卡片展示。
7. 以后可保存筛选视图，避免复制任务来满足不同查看方式。

当前仍只有四个固定问题阶段；没有模板编辑器、自动日报汇总、跟进时间专用字段、重复任务等。不要为了移植一口气加日历、番茄钟、复杂统计或新一套高/中/低优先级。

曾尝试访问 Todoist、Things、Microsoft To Do、TickTick 官方资料，但云网络返回代理 403，未完成实时市场调研。前面对产品的比较属于成熟设计参考，不是最新版本实测。华为官方最新资料也尚未核实。

## 6. 鸿蒙版：先验证平台，再决定工程和同步架构

### 已知环境缺口

旧云环境不能直接访问用户 Windows 电脑或设备。用户在电脑上打开网页聊天，不会自动授予本地终端、网络、IDE 或 USB 设备访问权限。需要本地支持工具执行的 Codex 客户端，并授权项目目录、终端和所需网络；以当前客户端实际能力为准。

尚未知：

- 两台设备“关于本机”的完整系统版本、型号标识。
- Windows 版本、DevEco Studio 是否安装、可用 SDK/API/设备类型。
- 华为开发者账号、认证、签名、证书、调试配置是否已有。
- 手机/手表连接、配对和设备调试能力。
- 实际可用的双端通信接口、后台条件、系统通知/提醒接口。

### 本地接续第一阶段：只做必要的能力确认

1. 读取本文件、README 和代码。检查当前分支、工作区改动，不覆盖用户文件，不 reset/clean。
2. 检查本地终端/网络权限和 Windows 工具：Git、Node；检测 DevEco Studio、其配套 SDK/运行时/构建工具、`hdc` 是否存在。不要打印整个进程环境、账号令牌或签名密码。
3. 从华为官方当前资料确认准确设备支持：DevEco Studio、SDK/API、手机与手表各自可用的应用模型/设备类型、ArkTS/ArkUI 能力。不要把完整智能手表和轻量穿戴、HarmonyOS 与其他平台混为一谈。
4. 官方开发入口：<https://developer.huawei.com/consumer/cn/>、<https://developer.huawei.com/consumer/cn/deveco-studio/>、<https://developer.huawei.com/consumer/cn/doc/>。这些是接续查询入口，不表示旧会话已读取最新页面。
5. 若已安装 IDE，优先使用匹配版本的官方配套工具和生成的工程模板；不要按记忆拼出假工程配置、随意安装不匹配 JDK，或宣称某个固定构建命令在所有版本通用。
6. 把确实缺少的信息一次性询问用户；工具/官方文档可以自己查到的先查，不要反复问已经明确的要求。账号登录、实名认证、验证码、手机/手表调试授权由用户本人完成；不索要聊天中的密码、令牌或私钥。

### 第二阶段：最小可行验证，必须真实跑通

先建立实际 SDK 支持的最小手机/手表工程，验证：

- 两端分别编译、签名、安装、启动。
- 两端各自新增一条事项、本地保存、退出/重开读取。
- 两端建立官方支持的通信链路，交换核心事项。
- 断连后两端修改、重连补同步，重复传输不产生重复事项。
- 完成/恢复/删除与编辑的冲突有明确且可测试的处理规则，不依赖单纯比较设备时钟。
- 调换顺序、子任务、问题字段都能完整同步。
- 两端分别验证提醒；测试锁屏、应用退出、设备重启、断连和重连时的真实行为，避免重复通知。

先输出可复现的构建/安装/运行命令和测试结果。没有真机证据就标注待验证，不用模拟器成功代替 Watch 5 真机兼容性。若官方通信能力受限，准确报告限制与替代方案，不先承诺任意蓝牙、局域网或后台方式一定可用。

### 第三阶段：再建设完整界面

- 建议采用受支持的鸿蒙原生技术（通常需要 ArkTS/ArkUI，最终按官方设备支持确定）。手机与手表可以各有模块，并共享模型/同步逻辑，但项目结构要在能力核实后决定。
- 手机参考现有今日工作台，按真实折叠/展开窗口宽度切换双栏/单栏，不凭设备名称硬编码尺寸。
- 手表可优先显示下一项和今日队列，再提供浏览其他核心事项的入口；小屏分层展示，不把手机整页缩小，也不取消用户要求的核心同步范围。
- 手机/手表离线修改先本地落盘，再可靠交换。需要考虑稳定实体 ID、更新操作标识、删除标记、重试幂等、首次全量与后续增量、并发排序和模式版本。
- 同步协议、主从/对等关系、冲突策略、数据库选择目前都**未定**。可提出方案并做验证，但不要将上述候选名词写成已实现能力。
- 不接 Windows 数据同步，不强制云服务，不上来就要求公网服务器。

### 本地目录与安全边界

可以考虑将未来鸿蒙源码放在独立 `harmony/` 目录下，保留当前桌面 `src/` 作为参考；这是组织建议，目录尚不存在。最终依当地 IDE 真实模板和工程要求确定。不要未经要求另建 GitHub 仓库或重构桌面代码。

签名材料、设备标识文件、账号凭据、本机 SDK 路径与缓存应按官方工程实际情况忽略，不能提交到 Git。首次需要联网安装工具/依赖，与运行时离线可用不是一回事。自用不代表免签名或永久免维护安装；须核对当前规则。

然后把根目录 `NEXT_CODEX_PROMPT.md` 的内容发送给新的本地 Codex 会话。第一次应先检查环境、查官方能力和创建最小验证工程，而不是直接声称鸿蒙版已经可安装。


这些是桌面参考版命令，不是鸿蒙编译命令。若本地网络对 npm/GitHub 有限制，先诊断代理和官方源，不关闭 TLS、签名或校验。依赖安装成功不等于完成手机/手表验收。

## 8. 接续完成标准与沟通偏好

- 用户希望直接推进能自主完成的工作，避免每一步都询问确认。
- 仅对实际缺少的信息、认证、设备授权或不可逆的操作请求用户配合；说明具体阻塞点。
- 工作过程用中文简洁说明进展，报告已验证、失败、未运行的项目，不夸大兼容性。
- 新会话不会自动继承原聊天；完整背景以此文件和根目录接续指令为准。能接续的前提是新会话确实读取到仓库文件，并有相应工具/权限。
- 首阶段完成标准：列出真实工具链和设备支持证据、工程结构、可重复命令、最小双端验证结果和明确剩余阻塞。
- 最终完成标准：两端自用安装可复现、核心事项完整同步、离线/重连/冲突/提醒经真机验证，文档可供未来再次接续。
